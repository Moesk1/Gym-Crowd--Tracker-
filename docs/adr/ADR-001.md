# ADR-001 — Use SQLite for Check-In Data Storage

## Context

The Gym Crowd Tracker needs to store student check-in and check-out information so that it can calculate the current crowd count accurately. The data needs to remain available even if the Flask application is stopped and restarted.

Because this is a small student project running locally, I needed a storage option that works with Python and Flask without requiring a separate database server or complicated setup. At the same time, simply keeping the data in Python memory would not be enough because the information would be lost whenever the application stops.

## Decision

I decided to use SQLite as the database for the Gym Crowd Tracker.

SQLite will store the student and check-in information used by the application. Flask will read and update this data when students check in or check out. The stored active check-ins will then be used to calculate the current crowd count and crowd level.

## Alternatives Considered

### 1. Store Data Only in Python Memory

One option was to store the students and active check-ins in Python lists or dictionaries.

This would be easier to build at the beginning because it would not require a database. However, all check-in information would be lost whenever the application stops or restarts. This would make it difficult to meet the requirement that check-in information is stored and used to calculate an accurate crowd count.

For that reason, I did not choose this option.

### 2. PostgreSQL

Another option was to use PostgreSQL.

PostgreSQL would provide more features for a larger application and would be better suited for many users accessing the database at the same time. However, it requires more setup and a separate database server. The current Gym Crowd Tracker is a small application being developed locally, so that extra complexity is not necessary for the first version.

For that reason, I did not choose PostgreSQL.

## Consequences

Using SQLite makes the first version of the application easier to develop because the database can be stored in a local file and does not require a separate database server. It also allows check-in information to remain stored after the Flask application is restarted.

However, this decision also creates limitations. SQLite is not as well suited as a larger database system for a high number of users writing data at the same time. If the Gym Crowd Tracker later becomes a larger application used by many gyms or many users at once, moving the data to a database such as PostgreSQL could require changes to the database configuration, queries, testing, and deployment process.

Choosing SQLite therefore keeps the current project simple, but it may make scaling the application to a much larger system more difficult later.
